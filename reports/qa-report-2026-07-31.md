### 2.4 Architecture Pattern: SyncContext

The refactoring introduces a `SyncContext` interface (`database-sync/types.ts`) that bundles the shared state previously accessed via `this`:

```typescript
interface SyncContext {
  doc: Y.Doc;
  localPeerId: string | null;
  activeBranchId: string | undefined;
  isReady: boolean;
  masterRole: string | null;
  metadata: Y.Map<string>;
  linkedNodes: Y.Map<LinkedNodeRecord>;
  ephemeralNodes: Map<string, Partial<LinkedNodeRecord>>;
  peerHistory: Map<string, ConnectionEvent[]>;
}
```

All extracted functions accept `SyncContext` as their first parameter instead of requiring class instances, enabling pure-function testing and easier mocking.

Similarly, `MessageHandlerContext` and `YjsSyncContext` provide the same pattern for the P2P layer.

### 4.2 Detailed Analysis of Top 3 Failure Categories

#### Category A: P2P Connection Timing (7 failures)

The P2P mesh initialization sequence requires:
1. PeerServer connection (~500ms)
2. PeerJS `open` event (~200ms)
3. `connect()` to discovered peers (~300ms per peer)
4. PQC handshake exchange (ML-KEM-768 encapsulate/decapsulate + ML-DSA-65 sign/verify: ~400ms)
5. AES key derivation via `importPQCSharedSecret()` (~100ms)
6. `ENCRYPTION_READY` exchange (~200ms)

Total: ~1.7s per peer for full mesh establishment. Tests using `waitForSelector` with default 5s timeout occasionally timeout when running parallel browser contexts (each consuming ~300ms of WebRTC setup time).

**Recommendation:** Increase E2E test timeout to 10s for P2P-dependent tests. Add a `waitForP2PReady()` helper that polls `dbSync.isReady` and `p2pManager.getConnectedPeerIds().length`.

#### Category B: Branch Switching Race (4 failures)

When `setActiveBranch()` is called, the flow is:
1. Local `dbSync.activeBranchId` is set
2. `SET_ACTIVE_BRANCH` message is broadcast
3. Remote peers update `peerBranches` map
4. Remote peers trigger `requestYjsSync()` for the new branch

Tests assert branch-scoped data immediately after step 1, before step 4 completes. The YJS diff exchange is asynchronous and network-dependent.

**Recommendation:** Add a `waitForBranchSync(branchId, timeoutMs)` helper that waits for `dbSync.activeBranchId === branchId` AND `dbSync.getStateVector()` to stabilize.

#### Category C: Encrypted Payload Timing (3 failures)

The dual-ready encryption path requires:
1. Both peers must have AES keys (`encryptionKeys` populated)
2. Both peers must have exchanged `ENCRYPTION_READY`

If peer A sends `YJS_UPDATE` before peer B has marked it as dual-ready, the update arrives as plaintext but the receiver expects ciphertext (or vice versa). The `shouldEncryptMessage()` function in `permissions.ts` handles this correctly at the type level, but the test timing creates a window where the guard fails.

**Recommendation:** In `message-handler.ts`, add a 500ms grace period after `ENCRYPTION_READY` before enforcing encryption. Alternatively, tests should wait for `p2pManager.isYjsAppEncryptedForPeer(targetPeerId)` before sending encrypted test data.
