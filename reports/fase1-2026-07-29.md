# 📊 Reporte Fase 1 — Modelo de Negocio Primario (Inventario + LLM en Navegador)

**Fecha:** 2026-07-29
**Analista:** Grok 4.5 High (via OpenClaw subagent)
**Estado general:** 🔶 **Funcional con deficiencias medias**

---

## Resumen Ejecutivo

El módulo de inventario de Shelf está operativo y ejecuta correctamente el CRUD de productos con variantes multi-atributo, persistencia local y exportación CSV. Los 35 tests unitarios del módulo pasan sin fallos (lib/ y api/). La arquitectura de variantes —soportando combinaciones cartesianas de color × medida × versión— está bien diseñada con funciones maduras como `normalizeProduct`, `mergeProductVariants` y `generateVariantsFromSelections`.

Sin embargo, se identificaron **4 problemas de severidad media (P1)** que afectan la confiabilidad del producto en producción:
1. **Falta de pruebas E2E y de integración** para el formulario de productos con variantes (solo existen tests unitarios de las funciones puras).
2. **No hay resolución de conflictos en ediciones concurrentes** —el merge de variantes simplemente suma cantidades sin estrategia de conflictos.
3. **AIChat expone datos completos de inventario** sin filtro de sensibilidad.
4. **La importación CSV carece de cobertura de tests**, a pesar de ser una funcionalidad core del negocio.

El WebLLM está funcional (Qwen2.5-1.5B-Instruct-q4f16_1-MLC) con sistema de fallback en cascada (local → Gemini Nano → Gemini API → OpenCodeGo → cloud API), pero el feature flag de AI está actualmente bloqueado tras la verificación `isPro`, lo cual limita el alcance de pruebas en desarrollo local.

## Problemas Medios (P1)

### P1-1: Sin resolución de conflictos en ediciones concurrentes

| Campo | Detalle |
|-------|---------|
| **Archivo** | `apps/shelf-inventory/lib/productVariants.ts` |
| **Líneas** | 167-175 (merge de variantes), 307-315 (merge de productos) |
| **Problema** | Las funciones `getProductVariants` y `mergeProductVariants` usan `buildVariantKey` como clave para merge, y cuando dos variantes tienen la misma clave, la cantidad simplemente se **suma** (`existing.quantity + variant.quantity`) y los precios/costos se sobreescriben sin criterio de resolución (`variant.price || existing.price`). No hay mecanismo de last-write-wins, vector clocks, ni estrategia CRDT. |
| **Impacto** | En un escenario multi-dispositivo con P2P mesh activo, dos peers editando la misma variante simultáneamente pueden causar duplicación de cantidades o precios inconsistentes. Los tests no cubren este escenario. |
| **Evidencia** | `merged.set(key, { ...existing, quantity: existing.quantity + variant.quantity, price: variant.price || existing.price })` — sin timestamp, sin vector clock, sin CRDT merge strategy |

### P1-2: AIChat expone datos completos de inventario sin filtro de sensibilidad

| Campo | Detalle |
|-------|---------|
| **Archivo** | `apps/shelf-inventory/components/AIChat.tsx` |
| **Líneas** | 61-91 |
| **Problema** | El contexto enviado al LLM incluye `name`, `sku`, `quantity`, `price`, `cost`, `colors`, `sizes`, `dimensions`, `material`, `capacity`, `customFields` y variantes anidadas de **todos los productos activos** (hasta 300 en modo cloud). Además envía sales (hasta 100) y auditLogs (hasta 50). No hay redacción de precios/costos sensibles. Aunque el modal muestra una nota de privacidad, la serialización completa de datos financieros ocurre antes del envío. |
| **Impacto** | Con el engine en modo `gemini` (API key del usuario) o en el fallback cloud API, los datos financieros completos del negocio viajan a servidores externos. No hay advertencia específica sobre esto. |
| **Evidencia** | `contextData.products.slice(0, productLimit).map(...)` incluye `price`, `cost`. No hay flag del tipo `redactSensitive` ni opción de configuración. |

### P1-3: Cobertura de tests insuficiente para funcionalidades core de negocio

| Campo | Detalle |
|-------|---------|
| **Archivos** | `apps/shelf-inventory/tests/crud-operations.spec.ts`, `apps/shelf-inventory/tests/` |
| **Problema** | Solo existen **5 files de test** cubriendo las 13+ features del FEATURES_STATUS (SRC-FUN-001 a SRC-FUN-014). `crud-operations.spec.ts` (206 líneas) es un test E2E de Playwright con un solo test CRUD y un test de ventas. No hay tests específicos para: formulario de producto con variantes, validación de SKU duplicados, batch image upload, importación CSV, export CSV, filtro de búsqueda multi-atributo, paginación móvil, pull-to-refresh, ni el AIChat. `ImportCSVModal` no tiene tests unitarios ni E2E. |
| **Impacto** | Riesgo alto de regresiones silenciosas. La importación CSV —funcionalidad core— no tiene ni un solo test. |
| **Evidencia** | `find apps/shelf-inventory -name '*.spec.*'` devuelve solo 5 archivos; `grep -l csv` no encuentra tests de importación CSV. |

### P1-4: `normalizeProduct` sobreescribe campos legacy sin preservar origen

| Campo | Detalle |
|-------|---------|
| **Archivo** | `apps/shelf-inventory/lib/productVariants.ts` |
| **Líneas** | 191-211 |
| **Problema** | La función `normalizeProduct` sobreescribe `color`, `dimensions`, `capacity`, `material` desde la primera variante (línea 201: `primaryVariant.attributes.Color || primaryVariant.attributes.color`). Si el producto fue migrado desde un sistema legacy donde estos campos estaban en el root del producto y las variantes no los tienen, se pierden. Además, en productos multi-variante, solo refleja el valor de la primera variante, dando una representación incompleta. |
| **Impacto** | Productos con variantes múltiples pueden mostrar atributos incorrectos en el catálogo si el usuario depende de los campos root. La función asume que la primera variante es representativa, pero no hay garantía. |
| **Evidencia** | `color: product.color || primaryVariant.attributes.Color || primaryVariant.attributes.color` — la cadena de `||` puede dar resultados inconsistentes en migraciones. |

## Observaciones adicionales

### Arquitectura general
Shelf tiene una arquitectura de variantes madura con **3 mecanismos complementarios**:
1. **Campos legacy root** (`color`, `dimensions`, `capacity`, `material`) — para compatibilidad
2. **VariantAttributes** (`string[]`) más **variants array** — para productos multi-variante
3. **CustomFields** (`Record<string, string>`) — para atributos arbitrarios del usuario

### Estado del PLAN-SHELF-REDESIGN
El plan de rediseño (Fase 2) propone eliminar el toggle "Artículo simple / Con variantes" y hacer detección automática multi-color/multi-medida directamente en el formulario. Esto es técnicamente factible con la infraestructura actual de `generateVariantsFromSelections`.

### Métricas del proyecto (desde FEATURES_STATUS.md)
- **Implementación general:** ~91% (21/21 features completas)
- **Inventory Management:** 96% (hardened) — la feature más madura
- **AI Assistant:** 86% (integrated) — la feature con % más bajo entre las implementadas

### Potenciales issues de rendimiento
- `getCustomFieldSummary` recalcula en cada render de cada fila de la tabla
- El contexto del AIChat serializa arrays completos de productos sin memoización
- `normalizeProduct` se llama en cada render sin memo, y recalcula variantes completas
